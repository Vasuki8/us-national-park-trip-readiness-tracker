# Visitor-facing notice history

This capability converts verified committed archive observations into a bounded visitor timeline. It is not an automatic publisher, a real-world event log or source-content permission. Production history is initially empty for all five parks. Synthetic populated histories exist only under `tests/` and the separate test-site output under `.superpowers/`.

## Data path and consistency

`tracker.history_projection.project_history(store, code, limit=20)` calls `HistoryStore.read` once. That read verifies the entire selected park chain and reconstructs its evidence. The projector returns a pair: `snapshot` (the exact current archived snapshot) and `history` (the visitor projection for the same head). It does not collect, write, alter a clock, read pending receipts or publish anything.

The website loads reviewed `data/history.json` and the existing `data/alerts/{code}.json`. `scripts/validate-history.ts` requires the history's canonical SHA-256 snapshot digest, head observation's collection status and check time to match the current snapshot. It validates exact allowed fields, safe official park-specific URLs, evidence digests, chronology, baseline/failure semantics and omitted counts. A retained successful-check timestamp must match the most recent visible successful observation, or predate an entirely failed truncated window. Where the visible event window is complete, reversing its changes must match the current notice hashes. Validation is part of loading website data, so a mismatched pair fails the Astro build.

A snapshot digest binds the displayed records and clocks, not the publisher's authenticity. Archive IDs are provenance references; the visitor file is not a standalone cryptographic proof of an entire archived chain. A party controlling the data can rewrite hashes. Promotion still requires trusted code, the verified archive and source-content review.

## Observation semantics

The first successful check is a baseline, not a batch of new closures. A later added/edited/removed item describes a difference between successful accepted feeds. Removed means **no longer present in the checked feed**, not a confirmed reopening. Failed and quarantined checks remain visible but generate no notice differences. An empty timeline does not mean that nothing changed; an unchanged comparison concerns only the checked feed.

Evidence panels retain the before/after title, description, category, source URL and normalized-record digest. Source text is ordinary escaped Astro text, never `set:html`. A currently reachable official link may have changed since the archived observation. Observation times are not NPS update times, effective dates or publication times. Date/area applicability is not inferred.

The browser recalculates age using the existing four-hour alert threshold every minute and when the page becomes visible. Static HTML always includes absolute check times and a no-JavaScript warning that age labels reflect the build. Historical evidence is not deleted when a freshness label expires.

## Bounds and omission

A projection contains at most 20 recent observations and 100 displayed changes per observation. `limit` may be lowered from 20 but not raised. Total and omitted observation/change counts are explicit. A history payload exceeding 2 MiB is refused, rather than silently truncating notice text. The returned current snapshot retains the archive's existing independent size bounds. The full archive is still subject to its disk/observation/reconstruction limits.

The viewer intentionally does not implement arbitrary history pagination, an unbounded export, a bulk-removal approval path, search-indexable date combinations or a public API endpoint. Earlier records are not deleted from the archive when omitted from the visitor view.

## Verification and production boundary

Python tests use the real history store and deterministic synthetic records. The shared `tests/fixtures/history-preview.json` is reproducibly generated by `tests/history_preview_fixture.py` and is validated independently by TypeScript. The isolated `tests/history-site/` builds the same timeline component for browser checks without adding fixture routes, environment overrides or synthetic conditions to the production site.

No private archive, pending receipt, key, provider response dump or actual NPS alert text is committed by this increment. There is no export/write CLI or workflow that promotes a candidate into website data. Before doing so: validate live source shapes, complete content-use review, persist the archive on operator-controlled storage, preserve the snapshot/history pair through staged publication and verify rollback. Site indexing, advertising and deployment remain separate gates.
